Seção 1

Apresentação do TraceAST-62304

1.1 O que é o TraceAST-62304?

O TraceAST-62304 é uma ferramenta computacional de triagem pré-auditoria baseada em evidências rastreáveis (evidence-traceable pre-audit screening) voltada para repositórios de código-fonte em Python que desenvolvem Software como Dispositivo Médico (Software as a Medical Device — SaMD).

Em vez de depender da intuição de um modelo de inteligência artificial generativa para "opinar" sobre um software, o TraceAST-62304 examina a estrutura física e sintática do repositório (usando Abstract Syntax Trees — AST), aplica 8 regras determinísticas versionadas (R01 a R08), recupera trechos pertinentes de documentos regulatórios oficiais (como a ANVISA RDC 657/2022 e mapeamentos da norma internacional IEC 62304) e gera um dossiê organizado em JSON e Markdown apontando exatamente em qual arquivo e em quais linhas cada evidência foi encontrada.

Explicação Simples para Entender em 30 Segundos

"Imagine uma empresa que está desenvolvendo um software médico. Antes de enviar o projeto para uma avaliação de qualidade ou regulatória, ela executa o TraceAST-62304. O sistema examina a estrutura do repositório, identifica evidências técnicas, verifica possíveis lacunas e organiza informações que precisam de atenção humana."

1.2 Qual problema ele pretende resolver e por que foi desenvolvido?

Equipes de pesquisa médica, hospitais universitários e startups de saúde digital frequentemente criam algoritmos promissores (por exemplo, redes neurais para triagem de radiografias de tórax), mas enfrentam dois problemas críticos quando precisam transformar esse código em um produto médico regularizado:

  1. Desconhecimento precoce de exigências de engenharia de ciclo de vida: Normas como a IEC 62304 e a RDC 657/2022 da ANVISA exigem controle rigoroso de bibliotecas de terceiros (chamadas de SOUP — Software of Unknown Provenance), verificação automatizada de unidades de software, tratamento seguro de falhas de leitura/escrita (I/O), validação de dados de entrada e separação controlada entre ambiente de treinamento e ambiente de produção. Descobrir essas lacunas apenas no momento da auditoria formal custa meses de retrabalho.
  2. Riscos de enviar código bruto para LLMs na nuvem: Copiar e colar o código inteiro de um software médico em um ChatGPT ou LLM comercial estoura o limite de memória do modelo (context window), expõe segredos industriais a servidores externos e produz "alucinações" (o modelo inventa cláusulas de lei que não existem ou afirma que o software está "aprovado").

O TraceAST-62304 foi desenvolvido exatamente para resolver essa lacuna: ele realiza toda a inspeção técnica do código localmente no computador do usuário, sem executar o código analisado e sem precisar enviar o código-fonte para a internet.

1.3 Quem pode utilizá-lo e como ele auxilia empresas de SaMD?

  • Desenvolvedores e Engenheiros de IA Médica: Para localizar rapidamente funções de leitura de dados sem bloco try-except, blocos except: pass que escondem erros, dependências sem versão fixada em requirements.txt ou scripts que misturam treinamento e inferência no mesmo arquivo.
  • Profissionais de Assuntos Regulatórios e Qualidade (QA/RA): Para obter um inventário completo dos arquivos do repositório (com códigos criptográficos SHA-256), lista preliminar de bibliotecas SOUP e indicação de quais documentos técnicos precisam ser cobrados da equipe de engenharia.
  • Pesquisadores em Informática Biomédica: Para conduzir estudos científicos reproduzíveis sobre maturidade de engenharia em repositórios de software médico.

1.4 Por que é uma ferramenta de PRÉ-AUDITORIA, e NÃO um auditor regulatório?

Uma auditoria regulatória real analisa o Sistema de Gestão da Qualidade (SGQ) da empresa, entrevistas com engenheiros, relatórios de testes clínicos, análise de gerenciamento de riscos (ISO 14971) e o comportamento do software funcionando na prática. Uma ferramenta que lê apenas os arquivos do repositório Git enxerga somente a "planta estrutural" do código. Por isso, o TraceAST-62304 atua como um check-up preliminar (pré-auditoria): ele prepara a equipe humana antes da auditoria oficial, mas jamais substitui o auditor humano.

1.5 O que o TraceAST-62304 consegue observar vs. O que NÃO consegue provar

Aspecto Analisado O que o sistema CONSEGUE observar com certeza (Fato Sintático) O que o sistema NÃO CONSEGUE provar sozinho (Exige Revisão Humana)
Arquivos e Sintaxe (R01) Quantos arquivos .py existem, seu hash SHA-256 e se todos possuem sintaxe Python válida. Não prova que o algoritmo faz o cálculo médico correto ou está livre de bugs lógicos.
Dependências / SOUP (R02) Se existe requirements.txt/pyproject.toml, quais pacotes têm versão fixada (==) e quais são importados no código. Não prova que a biblioteca externa é segura para o paciente nem substitui a matriz formal de risco de SOUP.
Testes e CI/CD (R03, R04) Se existem arquivos test_*.py, funções de teste e arquivos de workflow em .github/workflows/. Não prova que os testes passam na prática, nem que cobrem todos os requisitos críticos de segurança. A ausência de testes no repositório também não prova que a empresa não testa em outro ambiente.
Tratamento de Erros em I/O (R05) Se uma chamada open() ou pydicom.dcmread() está dentro de um bloco try-except e se o except está vazio (pass). Não prova que a ação tomada dentro do except protege o paciente contra dados corrompidos.
Validação de Entradas (R06) Se existem funções como validate_*, checagens isinstance() com raise ValueError ou instruções assert. Não prova que os limites clínicos ou fisiológicos (ex.: resolução de imagem DICOM ou faixa de batimentos cardíacos) estão corretos.
Modelos de IA e Treino/Inferência (R07, R08) Onde ocorrem chamadas torch.load(), arquivos .pt/.onnx e se chamadas backward() e forward() estão no mesmo arquivo ou em arquivos separados. Não prova a proveniência ética/clínica dos dados de treinamento nem garante que o servidor de produção hospitalar está fisicamente isolado.
Seção 2

Visão Geral do Funcionamento (Fluxo de Ponta a Ponta)

Quando você executa um comando de análise no TraceAST-62304, a função central run_pre_audit_pipeline() localizada em traceast/pipeline.py coordena 12 etapas encadeadas automaticamente. Nenhuma etapa exige copiar e colar dados manualmente.

2.1 Versão Simplificada (Para quem não tem experiência em programação)

Como o sistema trabalha em 5 passos simples
  1. Passo 1 — Recepção e Fichamento: Você indica a pasta do projeto médico e uma ficha descritiva opcional (perfil do produto). O sistema faz uma lista de todos os arquivos existentes e tira uma "impressão digital" (hash SHA-256) de cada um.
  2. Passo 2 — Raio-X da Estrutura (AST): Sem ligar ou executar o programa médico, o TraceAST-62304 desenha a "árvore genealógica" do código Python, anotando onde estão as classes, funções, leituras de arquivos, proteções contra erros, testes e bibliotecas.
  3. Passo 3 — Checklist de 8 Regras (R01 a R08): Um motor matemático fixo (determinístico) confere 8 indicadores técnicos sobre aquelas evidências coletadas e classifica cada um (por exemplo: Evidência identificada ou Evidência parcial).
  4. Passo 4 — Consulta à Biblioteca de Leis (RAG): Para cada uma das 8 regras, o sistema pesquisa em sua biblioteca local (RDC 657/2022 da ANVISA e guias IEC 62304) os 3 parágrafos mais parecidos com o tema da regra, anotando a página e seção. Se você quiser (opcional), uma IA traduz tudo para linguagem simples sem mudar o resultado técnico.
  5. Passo 5 — Impressão do Dossiê Final: O sistema confere se todos os dados estão completos e grava na pasta de saída um relatório legível (report.md) e arquivos técnicos auditáveis (findings.json e manifestos).

Explicação Detalhada de Cada Módulo

Nesta seção, abrimos a "caixa-preta" de cada arquivo Python do pacote traceast. Para cada módulo, explicamos sua razão de existir, suas classes e funções reais, parâmetros, retornos, tratamento de erros e exemplos práticos.

4.1 Módulo de Contratos e Validação: traceast/models.py

1. Finalidade e 2. Por que existe: Define o formato exato de todos os dados que circulam pelo sistema usando a biblioteca Pydantic V2. Ele existe para impedir que qualquer etapa (ou um modelo de linguagem externo) crie um achado incompleto, com número de linha negativo, com código de regra inválido ou sem justificativa/evidência.

3. Classes e Enums implementados:

  • FindingStatus(str, Enum): Restringe os estados permitidos a exatamente cinco opções: "observed", "not_observed", "partial", "unable_to_assess" e "not_applicable".
  • ReviewPriority(str, Enum): Define prioridades técnicas de revisão ("high", "medium", "low", "informational").
  • ConfidenceLevel(str, Enum): Confiança da regra estática ("high", "medium", "low").
  • MappingStatus(str, Enum): Situação da validação por especialista da referência normativa ("pending_expert_review", "reviewed", "approved_by_expert", "unverified").
  • ProductProfile(BaseModel): Armazena o contexto do dispositivo médico e possui o validador automático evaluate_unknown_fields().
  • EvidenceItem(BaseModel): Representa uma evidência individual extraída do código, com o validador validate_lines() que garante line_end >= line_start >= 1.
  • RegulatoryReference(BaseModel): Representa uma referência normativa (estática do catálogo ou recuperada pelo RAG).
  • LLMExplanationOutput(BaseModel): Contrato estrito da explicação opcional gerada por IA.
  • Finding(BaseModel): Representa um achado completo (ex.: TA-005), com o validador validate_finding_consistency().
  • RuleDefinition(BaseModel) e FindingsReport(BaseModel): Modelos do catálogo de regras e do documento JSON final.

4–6. Funções/Validadores críticos, parâmetros e retornos:

  • ProductProfile.evaluate_unknown_fields(self) -> ProductProfile: Verifica se intended_purpose ou clinical_decision_context estão vazios ou com strings como "unknown"/"desconhecido", ou se ai_components é None. Se sim, adiciona avisos explícitos na lista self.profile_limitations.
  • Finding.validate_finding_consistency(self) -> Finding: Verifica se o achado tem ao menos uma evidência em self.evidence OU um texto não vazio em self.justification. Caso contrário, dispara um ValidationError bloqueando a geração de achados sem lastro.

7–10. Exemplo de uso e Tratamento de Erros:

from traceast.models import EvidenceItem
# Exemplo válido:
ev = EvidenceItem(file="src/data_io.py", symbol="safe_load_dicom", line_start=25, line_end=30,
                  evidence_type="ast_io_call", description="Leitura DICOM protegida")
# Se line_end < line_start (ex: line_start=50, line_end=10), o Pydantic levanta ValidationError automaticamente!

4.2 Módulo de Configuração e Privacidade: traceast/config.py

1. Finalidade e 2. Por que existe: Centraliza todas as opções de execução, leitura do arquivo .env, listas de diretórios proibidos/sensíveis e carregamento do perfil YAML do produto. Existe para garantir que o sistema seja seguro por padrão (privacy-first): nunca exponha chaves de API nos relatórios e nunca envie dados para a nuvem sem ativação explícita.

3–6. Classes e Funções principais:

  • Classe TraceASTConfig: Recebe parâmetros opcionais (project_root, enable_rag=True, enable_llm=False, allow_code_excerpts_to_llm=False, excluded_dirs, embedding_model). No construtor __init__, carrega o .env e mescla as pastas padrão de exclusão (DEFAULT_EXCLUDED_DIRS) com eventuais pastas informadas em TRACEAST_EXCLUDE_DIRS.
  • Método has_groq_api_key(self) -> bool: Retorna True ou False indicando se a variável de ambiente GROQ_API_KEY foi configurada com uma chave real (diferente do texto de exemplo "your_api_key_here"), sem jamais imprimir ou retornar o valor da chave.
  • Método sanitized_Metadata(self) -> Dict[str, Any]: Retorna um dicionário seguro com os parâmetros da execução para ser gravado no run_manifest.json (contendo apenas "api_key_configured": True/False).
  • Função load_product_profile(profile_path: Optional[Path] = None) -> ProductProfile: Lê o arquivo YAML indicado em --profile usando yaml.safe_load() (que impede execução de objetos arbitrários em YAML). Se o arquivo não for informado ou não existir no disco, não interrompe a análise: retorna um ProductProfile padrão com a limitação documentada em profile_limitations.

4.3 Módulo Analisador Estático e Visitante AST: traceast/ast_analyzer.py

1. Finalidade e 2. Por que existe: É o "olho técnico" do TraceAST-62304. Inspeciona todos os arquivos do repositório sem executar nenhuma linha do código-alvo, extraindo a estrutura sintática de arquivos Python, dependências, testes e workflows de integração contínua.

3–6. Funções e Classes principais:

  • compute_sha256(file_path: Path) -> str: Lê o arquivo em blocos binários de 64 KB (65536 bytes) e retorna o hash criptográfico SHA-256 de 64 caracteres hexadecimais.
  • get_git_commit_sha(repo_path: Path) -> Optional[str]: Lê diretamente .git/HEAD e a referência da branch (ou executa git rev-parse HEAD com timeout de 5s) para identificar o commit exato analisado.
  • Classe FileASTVisitor(ast.NodeVisitor): Percorre recursivamente a árvore sintática de um arquivo Python mantendo a pilha self.scope_stack. Implementa:
    • visit_Import e visit_ImportFrom: Registra todos os módulos importados.
    • visit_ClassDef: Registra classes, classes-base (herança) e decoradores, empilhando ("class", node.name) em scope_stack antes de visitar os métodos internos.
    • _handle_function (chamado por visit_FunctionDef e visit_AsyncFunctionDef): Identifica se a função é de primeiro nível (top_level_function), método de classe (method / async_method) ou função aninhada dentro de outra função (nested_function / nested_async_function). Verifica sinais de validação, treinamento e inferência pelo nome e corpo da função.
    • visit_Try: Inspeciona blocos try-except-finally, extrai os tipos de exceção capturados e usa a função auxiliar _is_empty_or_pass_handler() para detectar se o bloco except está vazio ou contém apenas pass / ....
    • visit_Assert e visit_If: Detecta instruções assert e guardas condicionais que checam isinstance/None ou levantam exceções (raise).
    • visit_Call: Examina todas as chamadas de função do código (resolvendo nomes compostos como pydicom.dcmread ou torch.load via _get_call_name()). Cruza o número da linha da chamada (node.lineno) com os intervalos de linhas de self.try_blocks para saber com precisão matemática se uma operação de I/O está protegida por um bloco try-except não vazio (inside_non_empty_try).
  • parse_dependencies_from_repo(repo_path: Path, imported_modules: Set[str]) -> Dict[str, Any]: Lê *requirements*.txt, pyproject.toml (via tomllib nativo do Python 3.11+) e poetry.lock. Usa expressão regular para separar nome do pacote e versão, verifica se usa == e cruza com imported_modules usando o mapa de tradução PACKAGE_TO_IMPORT_MAP (que sabe, por exemplo, que o pacote scikit-learn é importado no código como sklearn e PyYAML como yaml).
  • inspect_tests_and_ci(repo_path: Path, parsed_files_data: List[Dict]) -> Dict[str, Any]: Localiza diretórios e arquivos de teste, frameworks (pytest, unittest) e lê arquivos YAML em .github/workflows/ e .gitlab-ci.yml extraindo comandos de teste e cobertura.
  • analyze_repository_static(repo_path: Path, excluded_dirs: Optional[Set[str]] = None) -> Dict[str, Any]: Função mestre do módulo que coordena toda a varredura, captura falhas de sintaxe/codificação sem interromper a execução e devolve o dicionário completo analysis.

4.4 Catálogo e Motor Determinístico de Regras: traceast/rule_catalog.py e traceast/rules_engine.py

1. Finalidade e 2. Por que existem: Separam a definição normativa/descritiva das regras (rule_catalog.py) da lógica algorítmica de avaliação (rules_engine.py). Isso permite calcular um hash criptográfico único do catálogo (compute_rule_catalog_hash()) para comprovar em um artigo científico que os critérios de avaliação não foram adulterados entre diferentes execuções.

Funções centrais em rules_engine.py:

  • _verify_evidence_against_repo(evidences: List[EvidenceItem], repo_path: Path) -> List[EvidenceItem]: Guardião anti-alucinação. Para cada evidência gerada, verifica se o arquivo repo_path / ev.file existe fisicamente no disco, conta quantas linhas reais o arquivo possui e garante que line_start e line_end estejam dentro do limite real do arquivo. Se um arquivo não existir, a evidência é descartada.
  • _eval_r01 até _eval_r08: Funções puras e determinísticas que avaliam cada uma das 8 regras e retornam um objeto Finding validado (explicadas uma a uma na Seção 7).
  • evaluate_all_rules(analysis: Dict, profile: ProductProfile, repo_path: Optional[Path]) -> List[Finding]: Executa sequencialmente as 8 regras e retorna a lista de achados TA-001 a TA-008.

4.5 Motor de Recuperação Regulatória (RAG): traceast/rag_engine.py

1. Finalidade e 2. Por que existe: Conecta cada regra técnica (`R01`–`R08`) aos documentos regulatórios reais presentes na pasta legal_documents/ (especificamente o PDF oficial da ANVISA RDC 657/2022 e os documentos de mapeamento da IEC 62304), recuperando os 3 trechos mais relevantes com rastreabilidade completa de página, seção e hash SHA-256.

Funções e Classes principais:

  • load_and_chunk_regulatory_corpus(legal_docs_dir: Path): Lê RDC_657_2022.pdf página por página com pypdf.PdfReader e lê os arquivos Markdown em templates_openregulatory/techdoc/62304/ e qms/software-validation/ (ignorando deliberadamente a pasta FDA/ conforme decisão de escopo da V1.0). Divide os textos com _chunk_text() e identifica cláusulas/artigos automaticamente com _extract_clause_or_section().
  • Classe RegulatoryRAGEngine: Constrói o índice de busca com scikit-learn (TfidfVectorizer(ngram_range=(1, 2), sublinear_tf=True)) para execução 100% local e instantânea, e suporta modo híbrido denso com SentenceTransformer quando TRACEAST_USE_DENSE_EMBEDDINGS=true. Seus métodos principais são retrieve_for_query(query_pt, query_en, top_k=3) e enrich_findings_with_rag(findings, top_k=3).

4.6 Módulo de Explicação Opcional via LLM: traceast/llm_agent.py

1. Finalidade e 2. Por que existe: Permite usar um Modelo de Linguagem (via API Groq) exclusivamente como tradutor didático dos achados técnicos para linguagem acessível, garantindo por código que o LLM jamais altere o status determinístico da regra nem receba código-fonte confidencial.

Funções principais:

  • build_sanitized_llm_payload(finding: Finding, allow_internal_names: bool = False) -> Dict: Extrai apenas contagens, tipos de evidência e números de linha, substituindo os nomes reais dos arquivos por "file_1.py" e símbolos por "symbol_1" quando allow_internal_names=False (padrão).
  • enrich_findings_with_optional_llm(findings, config, custom_llm_callable): Se config.enable_llm for False (padrão) ou a chave de API estiver ausente, retorna os achados originais intactos. Se ativo, solicita resposta em JSON, valida com LLMExplanationOutput.model_validate() e anexa ao campo llm_explanation. Qualquer erro de rede ou JSON inválido é capturado no bloco except Exception e registrado em llm_audit_log["errors"] sem interromper o pipeline.

4.7 Orquestração, Relatórios e Avaliação Científica: pipeline.py, reporting.py e evaluation.py

  • traceast/pipeline.py: Contém resolve_repository_target() (que aceita tanto caminhos locais quanto URLs Git remotas, limpando pastas temporárias no bloco finally) e run_pre_audit_pipeline(), que cronometra cada etapa com time.perf_counter() e monta os dicionários run_manifest e analysis_metrics.
  • traceast/reporting.py: Contém compute_summary_counts(), render_markdown_report() (que constrói as Seções A a F do arquivo report.md) e write_all_outputs() (que grava os 6 arquivos na pasta de saída).
  • traceast/evaluation.py: Contém generate_expert_annotation_templates(), compute_cohens_kappa(), classify_pair_outcome(), score_tool_against_consensus() (com reamostragem Cluster Bootstrap por repositório), evaluate_rag_recall_at_k() e generate_study_dataset_manifest().

Como Funciona a Análise AST (Abstract Syntax Tree)

Conceito Fundamental: O que é uma AST?

"Uma árvore sintática abstrata é uma representação organizada da estrutura de um programa. Em vez de apenas ler o código como texto, o analisador consegue identificar funções, classes, imports e estruturas de controle."

6.1 Por que usar AST em vez de procurar palavras no texto (Ctrl+F / Regex)?

Se você usar uma busca simples de texto (Ctrl+F) procurando a palavra torch.load ou open( em um arquivo Python, um simples comentário explicativo (ex.: # Nunca use open() sem cuidado) ou um texto de ajuda (docstring) enganaria o sistema, gerando um Falso Positivo.

Quando o Python transforma o arquivo em uma AST através da função nativa ast.parse(), comentários são descartados e textos entre aspas viram apenas nós constantes (ast.Constant), enquanto uma chamada real de função no programa vira um nó estrutural do tipo ast.Call. É exatamente assim que a fixture negativa repo_false_positive_traps/scheduler.py é testada na suíte do projeto: ela contém textos mencionando torch.load('model.pt') dentro de strings, e o analisador AST acerta ao reportar zero chamadas reais!

6.3 Detalhamento de Como Cada Estrutura é Identificada

  • Descoberta e Abertura de Arquivos: os.walk(repo_path) percorre todas as subpastas removendo DEFAULT_EXCLUDED_DIRS. Cada arquivo .py é lido em bytes (py_file.read_bytes()), tem seu SHA-256 calculado e é decodificado com raw_bytes.decode("utf-8-sig") (que suporta arquivos UTF-8 com ou sem BOM do Windows).
  • Classes, Métodos, Funções Aninhadas e Assíncronas: Graças à pilha self.scope_stack em traceast/ast_analyzer.py (linhas 348–359):
    • Se o topo da pilha é vazio, a função é top_level_function (ou async_function se for ast.AsyncFunctionDef).
    • Se o topo da pilha é "class", a função é um método da classe (method ou async_method).
    • Se o topo da pilha já é outra função ou método (parent_kind != "class"), a função é identificada como função aninhada (nested_function ou nested_async_function, como validate_dicom_input._nested_range_validator).
  • Blocos try-except e Capturas Silenciosas (pass): A função _is_empty_or_pass_handler() inspeciona o corpo de cada ast.ExceptHandler. Se o bloco except contiver apenas a instrução pass (ast.Pass), reticências ... ou uma string solta sem nenhuma ação real, ele é marcado com has_empty_except=True e has_pass_in_except=True.
  • Sinais de Treinamento vs. Inferência: O visitante combina dois critérios: (a) nomes de funções/métodos (ex.: train*, fit_model* para treino; forward, predict*, infer* para inferência) e (b) chamadas de métodos na AST (backward(), step(), zero_grad(), .train() para treino; .eval(), no_grad(), inference_mode() para inferência).
  • Tratamento de Erros de Parsing: Se um arquivo Python tiver erro de digitação (como def broken_clinical_function(x, y: em broken_syntax.py), o bloco except SyntaxError as e: captura o erro, registra o nome do arquivo, o SHA-256, a linha exata do erro (e.lineno) e a mensagem do interpretador em failed_files, e continua analisando o restante do repositório.

Como Funciona o RAG (Retrieval-Augmented Generation)

Analogia Didática: O que é RAG?

"Imagine que o sistema possui uma biblioteca de documentos técnicos. Em vez de pedir ao modelo para responder apenas com aquilo que aprendeu durante o treinamento, o RAG procura trechos relevantes nessa biblioteca e disponibiliza essas informações como contexto."

8.1 Diagrama do Pipeline RAG Implementado em traceast/rag_engine.py

8.2 As 13 Etapas Internas do RAG Explicadas

  1. Como os documentos são carregados: A função load_and_chunk_regulatory_corpus() em traceast/rag_engine.py localiza legal_documents/RDC_657_2022.pdf e os arquivos .md dentro de legal_documents/templates_openregulatory/techdoc/62304/ e qms/software-validation/ (26 arquivos ao todo). A pasta FDA/ é propositalmente ignorada na V1.0.
  2. Como o texto é extraído: Para o PDF da ANVISA, utiliza pypdf.PdfReader extraindo o texto de cada página numerada (enumerate(reader.pages, start=1)). Para os arquivos Markdown, lê em UTF-8 via md_path.read_text(encoding="utf-8"). Antes de extrair, calcula o hash SHA-256 do arquivo original.
  3. O que são Chunks (Fragmentos): São pedaços menores de texto (de 900 a 950 caracteres) nos quais um documento longo é fatiado.
  4. Por que os documentos são divididos em Chunks: Uma lei inteira tem dezenas de páginas. Se não dividirmos em pedaços pequenos, uma busca sobre "SOUP" retornaria a lei inteira sem apontar o artigo ou parágrafo específico.
  5. O que significa Overlap (Sobreposição): Ao cortar um texto no caractere 900, uma frase importante poderia ser partida ao meio. Por isso, o próximo pedaço não começa no caractere 901: ele volta 150 a 180 caracteres para trás (overlap=150 para PDF e overlap=180 para Markdown), repetindo o finalzinho do trecho anterior para preservar o sentido completo da frase.
  6. O que são Embeddings e Representações Vetoriais: Computadores não comparam textos por significado usando letras diretamente; eles convertem cada texto em uma lista de números (um vetor matemático). Textos que falam do mesmo assunto produzem vetores que apontam para a mesma direção no espaço matemático.
  7. Como os textos são convertidos em vetores no código real: O TraceAST-62304 utiliza por padrão o vetorizador bilíngue TfidfVectorizer(ngram_range=(1, 2), sublinear_tf=True) do scikit-learn (que cria vetores matemáticos de palavras e pares de palavras sem depender de download na internet), e quando TRACEAST_USE_DENSE_EMBEDDINGS=true, combina esse vetor (peso 35%) com o vetor neural denso de 384 dimensões do modelo sentence-transformers/all-MiniLM-L6-v2 (peso 65%).
  8. Como funciona a busca por similaridade (Similaridade de Cosseno): A função cosine_similarity(q_tfidf, self._tfidf_matrix) calcula o cosseno do ângulo entre o vetor da pergunta da regra e o vetor de cada um dos 257 fragmentos da biblioteca. O resultado varia de 0.0 (nenhuma semelhança) até 1.0 (idêntico).
  9. Sobre o ChromaDB e Persistência Local: O pacote chromadb==1.5.9 faz parte do ambiente do projeto, e na V1.0 o motor RegulatoryRAGEngine.persist_index() também salva um índice determinístico auditável em JSON (db_regulacao_v1/rag_corpus_index.json) contendo todos os documentos, hashes SHA-256 e os 257 fragmentos numerados, garantindo reprodutibilidade exata em qualquer sistema operacional.
  10. Como são selecionados os fragmentos recuperados: A função np.argsort(final_scores)[::-1][:top_k] ordena os 257 fragmentos do maior score para o menor e seleciona os 3 primeiros (top_k=3).
  11. Como os metadados são preservados: Cada fragmento carrega seu dicionário completo: chunk_id (ex.: IEC62304_OPENREG_SOUP::s01 ou ANVISA_RDC_657_2022::p004::c01), document_id, name, issuing_body, page, section_or_clause (extraído automaticamente por regex que detecta Art. X ou seções da IEC 62304), document_hash e similarity_score.
  12. Como o resultado chega aos achados e ao agente: O método enrich_findings_with_rag() transforma cada um dos 3 fragmentos recuperados em um objeto RegulatoryReference e o adiciona à lista finding.regulatory_references do respectivo achado, além de gravar a trilha completa em retrieval_trace.json.
  13. O que acontece quando nenhum documento é encontrado: Se a pasta legal_documents/ estiver vazia ou ausente, self.chunks fica vazia, retrieve_for_query() retorna [] sem travar o programa, e o achado mantém apenas as referências estáticas do catálogo.

Grupo A — Métricas de Inspeção e Análise Estrutural do Repositório

A.1 Cobertura de Inspeção Sintática (inspection_coverage_percent)

O que mede tecnicamente: A proporção percentual de arquivos Python (.py) descobertos no repositório que foram convertidos com sucesso em Árvores de Sintaxe Abstrata (AST) sem erros léxicos, sintáticos ou de codificação de caracteres.
Em palavras simples: De todos os arquivos de código Python que existem na pasta do projeto, quantos por cento a ferramenta conseguiu ler do começo ao fim sem tropeçar em erros de digitação?
Por que essa métrica é importante para o TraceAST-62304: Responde à pergunta: "Posso confiar que o relatório enxergou todo o código Python do repositório, ou algum arquivo ficou de fora porque estava corrompido?"
Como é calculada: inspection_coverage_percent = (python_files_parsed_successfully / python_files_found) * 100
Onde: python_files_parsed_successfully é o número de arquivos .py analisados sem erro, e python_files_found é o total de arquivos .py encontrados (python_files_parsed_successfully + python_files_failed).
Exemplo prático: Na fixture repo_deficient_and_coupled, existem python_files_found = 2 arquivos Python (model_pipeline.py e broken_syntax.py). Apenas 1 foi analisado com sucesso e 1 falhou. Logo: (1 / 2) * 100 = 50.0%.
Como interpretar o resultado: 100.0%: Todos os arquivos Python foram inspecionados pela AST.
Entre 0.1% e 99.9%: Pelo menos um arquivo Python tem erro de sintaxe ou leitura; o código dentro daquele arquivo específico não pôde ser verificado pelas regras R05–R08.
0.0%: Nenhum arquivo Python existe no repositório ou todos estão com sintaxe quebrada.
O que essa métrica NÃO prova: Ter 100.0% de cobertura de inspeção não tem nenhuma relação com "cobertura de testes (test coverage)" e não prova que o software está em conformidade com a IEC 62304; prova apenas que o código-fonte possui sintaxe Python legível.

A.2 Contagens de Evidências e Sinais Estruturais (structural_counts e all_evidences)

O que mede tecnicamente: A frequência absoluta de cada categoria de nó sintático extraído pela classe FileASTVisitor e pelos inspetores de manifesto em todo o repositório (total_classes, total_functions_and_methods, nested_functions, async_functions_and_methods, total_try_blocks, empty_or_pass_except_blocks, total_io_operations, total_validation_signals, total_model_artifact_signals, total_training_signals, total_inference_signals).
Em palavras simples: É o inventário quantitativo de quantas peças de cada tipo (quantas funções, quantos blocos de proteção de erro, quantas leituras de arquivo, quantas chamadas de treino/inferência) existem dentro do código.
Por que essa métrica é importante para o TraceAST-62304: Fornece a matéria-prima numérica para que as regras determinísticas R01–R08 tomem decisões transparentes.
Como é calculada e Exemplo prático: Soma direta dos elementos extraídos em cada arquivo analisado: por exemplo, em demo_well_structured, total_io_operations = 3 (1 em data_io.py, 1 em trainer.py, 1 em inference.py) e empty_or_pass_except_blocks = 0.
Como interpretar o resultado: Em empty_or_pass_except_blocks, o valor desejável em engenharia segura é 0 (nenhum erro sendo silenciado com pass). Já contadores como total_io_operations ou total_classes descrevem o porte e o perfil do código, não sendo "melhores" ou "piores" por serem maiores.
O que essa métrica NÃO prova: Contar total_validation_signals = 7 mostra que há 7 pontos de checagem no código, mas não prova que todas as entradas clínicas perigosas foram validadas.

Grupo B — Métricas de Validação Científica dos Achados (Comparação com Especialistas)

B.1 True Positive (TP), False Positive (FP), False Negative (FN) e True Negative (TN)

O que mede tecnicamente: A matriz de confusão binária calculada pela função classify_pair_outcome(tool_status, human_status) em traceast/evaluation.py ao comparar o estado emitido pela ferramenta com o consenso dos especialistas humanos para cada par (repository_id, rule_id). Estados com presença de sinal (observed, partial) são tratados como positivos, e ausência (not_observed) como negativo. Quando o humano julga a regra not_applicable ou unable_to_assess, se a ferramenta retornar not_observed ou not_applicable, o código classifica como TN (não penalizando como falso negativo).
Em palavras simples:
  • True Positive (TP — Verdadeiro Positivo): O especialista disse que o indicador/evidência existe, e o TraceAST-62304 também o encontrou. (Acerto!)
  • False Positive (FP — Alarme Falso): O TraceAST-62304 apontou um indicador/evidência, mas o especialista humano verificou que ele não existe ou era inaplicável. (Erro de excesso!)
  • False Negative (FN — Omissão): O indicador existia no repositório segundo o especialista humano, mas o TraceAST-62304 deixou passar (retornou not_observed). (Erro de omissão!)
  • True Negative (TN — Verdadeiro Negativo): O indicador realmente não existia (ou não se aplicava), e o TraceAST-62304 corretamente não o apontou. (Acerto!)
Por que essa métrica é importante para o TraceAST-62304: Separa os dois tipos de erro que uma ferramenta de triagem pode cometer: gerar ruído desnecessário para a equipe (FP) versus deixar passar um ponto importante sem avisar (FN).
Como é calculada e Exemplo prático: Contagem direta em score_tool_against_consensus(). Se avaliarmos 10 repositórios com 8 regras cada (80 avaliações) e obtivermos TP=44, FP=5, FN=1, TN=30, a soma é 44 + 5 + 1 + 30 = 80.
Como interpretar o resultado: Em uma ferramenta de triagem pré-auditoria, um número baixo de FN indica que poucas evidências reais escapam da varredura, enquanto um número baixo de FP indica que os desenvolvedores perderão pouco tempo investigando alarmes falsos.
O que essa métrica NÃO prova: As contagens brutas (TP, FP, FN, TN) dependem do tamanho da amostra; por isso precisam ser convertidas em taxas relativas (Precision, Recall e F1).

B.2 Precision (Precisão), Recall / Sensitivity (Sensibilidade) e F1-Score

O que mede tecnicamente:
  • Precision: Fração das detecções positivas da ferramenta que são verdadeiras segundo o padrão de referência humano.
  • Recall (Sensitivity): Fração do total de casos positivos reais (segundo os especialistas) que a ferramenta conseguiu detectar.
  • F1-Score: Média harmônica entre Precision e Recall, penalizando desequilíbrios extremos entre ambas.
Em palavras simples:
  • Precision responde: "Quando o TraceAST-62304 aponta alguma coisa, qual a chance de ele estar certo?"
  • Recall responde: "De tudo o que realmente existia para ser encontrado no código, quanto o TraceAST-62304 conseguiu achar?"
  • F1-Score responde: "Qual é a nota combinada de equilíbrio entre não inventar alarmes falsos (Precision) e não deixar passar nada (Recall)?"
Por que essas métricas são importantes para o TraceAST-62304: Se uma ferramenta tivesse Recall = 100% simplesmente chutando que "tudo está presente em todos os arquivos", sua Precision seria péssima. Se ela só apontasse 1 caso óbvio para ter Precision = 100%, seu Recall seria péssimo. Avaliar as três juntas garante rigor científico na publicação.
Como são calculadas (Fórmulas em _compute_prf1()):
  • Precision = TP / (TP + FP)
  • Recall = TP / (TP + FN)
  • F1 = (2 * Precision * Recall) / (Precision + Recall)
(Nota: O código calcula tanto a versão Micro — somando TP, FP e FN de todas as regras antes de dividir — quanto a versão Macro — calculando a média simples das 8 regras).
Exemplo Didático Obrigatório (Passo a Passo com Números Fictícios para Ensino):

Imagine que dois especialistas humanos analisaram um repositório e identificaram 10 possíveis lacunas/indicadores reais. Ao rodar o TraceAST-62304, a ferramenta apontou 8 lacunas. Comparando as listas, verificou-se que 6 das 8 apontadas pela ferramenta também foram identificadas pelos especialistas:

  • Os 6 achados corretos são os True Positives (TP = 6).
  • Os 2 achados que a ferramenta apontou, mas os especialistas não confirmaram (`8 - 6 = 2`), são os False Positives (FP = 2).
  • As 4 lacunas que os especialistas identificaram, mas a ferramenta deixou passar (`10 - 6 = 4`), são os False Negatives (FN = 4).

Cálculo passo a passo:

  • Precision: 6 / (6 + 2) = 6 / 8 = 0.75 (75%) → "De tudo que a ferramenta apontou, 75% foi confirmado pelos especialistas."
  • Recall: 6 / (6 + 4) = 6 / 10 = 0.60 (60%) → "De todas as lacunas identificadas pelos especialistas, a ferramenta conseguiu encontrar 60%."
  • F1-Score: (2 * 0.75 * 0.60) / (0.75 + 0.60) = 0.90 / 1.35 = 0.6667 (66.67%) → Combina Precision (75%) e Recall (60%) pela média harmônica.

*Estes números (10, 8, 6) são fictícios e exclusivos para ensino didático do método de cálculo.

Como interpretar o resultado: Valores variam de 0.0 (0%) a 1.0 (100%). Na triagem pré-auditoria, prioriza-se alto Recall (ex.: ≥ 0.85) para evitar que lacunas passem despercebidas antes da auditoria humana, mantendo Precision adequada (ex.: ≥ 0.80) para não sobrecarregar a equipe. Um valor igual a 0.0 significa que nenhum achado verdadeiro foi acertado (`TP = 0`).
O que essa métrica NÃO prova: Mesmo um F1-Score = 0.95 em indicadores sintáticos não significa que a ferramenta substitui o auditor humano em tarefas semânticas ou clínicas.

B.3 Coeficiente Kappa de Cohen (inter_rater_agreement_cohens_kappa)

O que mede tecnicamente: O grau de concordância inter-avaliadores (inter-rater reliability) entre o Especialista Humano 1 e o Especialista Humano 2 ao classificarem independentemente os mesmos repositórios, descontando a proporção de concordância que ocorreria puramente por sorte/acaso.
Em palavras simples: Mede se os dois especialistas humanos realmente entendem e aplicam as regras do mesmo jeito, descontando os acertos que aconteceriam por pura coincidência se eles estivessem chutando.
Por que essa métrica é importante para o TraceAST-62304: Antes de cobrar que o software acerte o gabarito dos especialistas, precisamos provar para os revisores da revista científica (*JMIR Medical Informatics*) que o próprio gabarito humano é confiável e consistente!
Como é calculada (Função compute_cohens_kappa() em traceast/evaluation.py): kappa = (P_o - P_e) / (1 - P_e)
Onde: P_o é a proporção de concordância observada na prática, e P_e é a soma das probabilidades de ambos escolherem a mesma categoria ao acaso: P_e = Σ [ P_1(cat) * P_2(cat) ].
Exemplo Didático Obrigatório (Por que concordar muito pode enganar sem o Kappa):

Suponha que dois especialistas avaliem 10 itens usando apenas observed ou not_observed (exemplo fictício para ensino):

  • Ambos dizem observed em 8 itens, ambos dizem not_observed em 1 item, e discordam em 1 item (Avaliador 1 diz observed e Avaliador 2 diz not_observed).
  • À primeira vista, eles concordaram em 9 de 10 itens (P_o = 9/10 = 0.90 ou 90%). Parece quase perfeito!
  • Porém, como quase tudo era observed (Avaliador 1 marcou observed em 90% das vezes e Avaliador 2 em 80%), a chance de concordarem por puro acaso já era enorme: P_e = (0.90 * 0.80) + (0.10 * 0.20) = 0.72 + 0.02 = 0.74 (74%)!
  • Aplicando a fórmula do Kappa: kappa = (0.90 - 0.74) / (1.0 - 0.74) = 0.16 / 0.26 = 0.6154. Ou seja, descontando o acaso, a concordância real foi moderada/substancial (0.615), e não 0.90!
Como interpretar o resultado: 1.0 indica concordância perfeita; > 0.80 concordância excelente; 0.61 a 0.80 substancial; 0.0 indica concordância igual ao puro sorteio aleatório; valores negativos indicam concordância pior que o acaso.
O que essa métrica NÃO prova: O Kappa sofre do "paradoxo da prevalência": se uma categoria for extremamente rara ou extremamente comum (como no exemplo acima), o valor do Kappa pode cair mesmo quando os avaliadores concordam em 90% dos casos. Por isso, deve ser sempre relatado junto com a porcentagem simples de concordância (P_o).

Grupo C — Métricas de Recuperação Documental (RAG)

C.1 Recall@3 da Recuperação RAG (hit_rate_recall_at_k e mean_fractional_recall_at_k)

O que mede tecnicamente: Avalia a eficácia do sistema de busca documental (`RegulatoryRAGEngine`) ao verificar se os documentos normativos relevantes esperados para cada consulta de teste aparecem entre os k = 3 fragmentos mais bem ranqueados retornados pelo buscador.
Em palavras simples (Exemplo Didático Obrigatório): "Imagine que um especialista determinou que o trecho relevante para uma pergunta regulatória está no documento A, página 12. O sistema faz uma pesquisa e retorna três fragmentos. Se o trecho esperado estiver entre os três retornados, essa consulta foi recuperada com sucesso."
Por que essa métrica é importante para o TraceAST-62304 e Diferença para o Recall dos Achados: Não confunda! O Recall dos Achados (Grupo B) mede se o analisador de código encontrou os problemas no Python. Já o Recall@3 do RAG (Grupo C) mede se o buscador de leis trouxe os documentos normativos certos nas 3 primeiras posições para ajudar a explicar aquela regra.
Como é calculada (Função evaluate_rag_recall_at_k() em traceast/evaluation.py): Para cada consulta $i \in \{1, \dots, Q\}$ com conjunto de documentos esperados $E_i$ e conjunto recuperado nas 3 primeiras posições $R_{i,3}$:
1. Hit Rate Recall@3: Proporção de consultas em que houve ao menos 1 acerto: hits_at_3 / total_queries (onde hit = 1 se $|E_i \cap R_{i,3}| \ge 1$).
2. Fractional Recall@3: Média da cobertura das referências esperadas por consulta: $\frac{1}{Q} \sum_{i=1}^{Q} \frac{|E_i \cap R_{i,3}|}{|E_i|}$.
Exemplo prático real (em evaluation_artifacts/rag_recall_at_3_evaluation.json): Nas total_queries = 8 consultas (uma para cada regra Q_R01 a Q_R08), todas as 8 trouxeram ao menos um documento esperado entre os 3 primeiros: hit_rate_recall_at_k = 8 / 8 = 1.0 (100%), e a média fracionária foi 0.5417 (54.17%).
Como interpretar o resultado: hit_rate_recall_at_k = 1.0 significa que nenhuma regra ficou "órfã" de um documento pertinente no Top-3. Um valor próximo de 0.0 indicaria que os termos de busca das regras estão desconectados do vocabulário dos documentos normativos.
O que essa métrica NÃO prova: Trazer o documento certo entre os 3 primeiros não garante que a interpretação jurídica daquele artigo para o produto específico esteja exaurida sem leitura pelo especialista.

C.2 Score de Similaridade de Cosseno (similarity_score)

O que mede tecnicamente: O produto interno normalizado ($\cos(\theta) = \frac{\mathbf{q} \cdot \mathbf{d}}{\|\mathbf{q}\| \|\mathbf{d}\|}$) entre o vetor da consulta da regra ($\mathbf{q}$) e o vetor do fragmento documental ($\mathbf{d}$).
Em palavras simples: É uma nota de 0.0 a 1.0 que mede o quão parecido é o vocabulário/assunto da pergunta da regra com o texto daquele pedaço de norma.
Por que é importante e Como é calculada: Calculada em retrieve_for_query() via cosine_similarity (ou combinação ponderada 0.65 * dense + 0.35 * lexical quando embeddings densos estão ativos). Permite ordenar os 257 fragmentos e mostrar ao usuário quão forte foi a correspondência textual.
Exemplo prático e Interpretação: Na regra R02 (SOUP), o fragmento IEC62304_OPENREG_SOUP::s01 obteve similarity_score = 0.5173 (alta sobreposição de termos específicos como SOUP, 8.1.2, 5.3.3). Em modelos TF-IDF com centenas de palavras, scores acima de 0.20 já indicam forte compartilhamento de termos técnicos específicos.
O que essa métrica NÃO prova: O score de similaridade não é uma probabilidade estatística de obrigatoriedade legal; mede apenas proximidade lexical/semântica entre textos.

Grupos E & F — Métricas Estatísticas (Intervalo de Confiança / Cluster Bootstrap) e Eficiência

F.1 Intervalo de Confiança de 95% via Cluster Bootstrap por Repositório (confidence_intervals_95)

O que mede tecnicamente: A faixa de variação amostral das estimativas de Precision, Recall e F1-Score obtida por reamostragem não-paramétrica com reposição (Cluster Bootstrap, $B = 500$ ou $1000$ iterações) entre os percentis $2.5\%$ e $97.5\%$, tratando cada repositório completo (repository_id) como unidade primária de amostragem (cluster).
Em palavras simples (Exemplo Didático Obrigatório): "O resultado calculado em uma amostra pode ser diferente do resultado que encontraríamos em outros repositórios. O intervalo de confiança representa uma forma de expressar a incerteza da estimativa."
Cuidado Estatístico Essencial (O que significa "95% de Confiança"): Um Intervalo de Confiança de 95% (ex.: F1 entre 0.8913 e 0.9787) NÃO significa que existe 95% de probabilidade de o valor verdadeiro estar dentro desse intervalo específico já calculado (pois o valor verdadeiro na população é fixo, não aleatório). O significado correto é: se repetíssemos o procedimento de coleta e cálculo em centenas de amostras independentes de repositórios do mesmo tamanho, 95% dos intervalos construídos por esse método cobririam o valor verdadeiro da população.
Por que o REPOSITÓRIO (e não cada achado isolado) é a unidade de reamostragem? Dentro de um mesmo repositório, as 8 regras não são independentes: elas refletem a mesma equipe de programadores e o mesmo estilo de código. Se sorteássemos achados individuais misturados, fingiríamos ter $20 \times 8 = 160$ amostras independentes, estreitando artificialmente o intervalo de confiança (erro estatístico chamado de pseudorreplicação). Ao sortear repositórios inteiros com todas as suas 8 regras juntas em score_tool_against_consensus() (linhas 162–180 de traceast/evaluation.py), respeitamos a estrutura real do estudo!
Exemplo prático e Interpretação: Com 10 repositórios sintéticos ($B = 500$), obtivemos F1 = 0.9362 com IC 95% [0.8913, 0.9787]. Intervalos muito largos (ex.: [0.45, 0.98]) indicam que a amostra de repositórios ainda é pequena ou muito heterogênea; intervalos estreitos indicam maior precisão da estimativa amostral.
O que essa métrica NÃO prova: O intervalo de confiança mede apenas a incerteza amostral; ele não corrige vieses de seleção (por exemplo, se todos os 20 repositórios escolhidos forem do mesmo autor).

E.1 Métricas de Eficiência: Tempo por Etapa (durations_seconds) e Consumo de Tokens (total_tokens)

O que medem tecnicamente e Como são calculadas: Em traceast/pipeline.py, o relógio de alta precisão time.perf_counter() mede o tempo gasto em cada fase (ast_and_inventory, rules_engine, rag_retrieval, llm_explanations e total_pipeline). Em traceast/llm_agent.py, quando o LLM está ativo, soma-se usage.prompt_tokens e usage.completion_tokens retornados pela API.
Em palavras simples e Exemplo prático: Mostram quantos segundos cada peça do programa demorou para trabalhar (ex.: 1.3558 segundos para analisar todo o repositório do TraceAST-62304 com 24 arquivos Python) e quantos tokens foram consumidos na nuvem (0 tokens no modo padrão local).
O que essa métrica NÃO prova: Execução rápida demonstra viabilidade prática em pipelines de desenvolvimento, mas velocidade de processamento não tem relação com qualidade regulatória do software analisado.

Transparência sobre Métricas Não Implementadas na V1.0

Conforme a regra de fidelidade estrita ao código real, informamos explicitamente que as seguintes métricas mencionadas em discussões teóricas NÃO estão implementadas como cálculos automáticos no código da V1.0:

Seção 15

Entendendo as Limitações Técnicas, Clínicas e Científicas

15.1 Ausência de Evidência NÃO é Evidência de Ausência

Na filosofia da ciência e em auditoria regulatória, vale o princípio: "Ausência de evidência não é evidência de ausência". Quando o TraceAST-62304 atribui o status not_observed (por exemplo, na regra R03 por não encontrar uma pasta tests/), isso significa exclusivamente que não há arquivos de teste visíveis naquele repositório Git. A equipe pode manter os testes em outro repositório ou em uma plataforma externa de gestão da qualidade. Por isso, o sistema jamais traduz not_observed como "não conformidade".

15.2 Como Podem Ocorrer Falsos Positivos e Falsos Negativos nas Heurísticas

Regra Como pode ocorrer um Falso Positivo (Alarme Excessivo) Como pode ocorrer um Falso Negativo (Omissão Sintática)
R02 (Dependências) Um módulo interno importado via manipulação dinâmica de sys.path em subpasta pode parecer um pacote externo não declarado em requirements.txt. Uma biblioteca carregada dinamicamente via importlib.import_module(nome_variavel) não aparece como nó ast.Import estático.
R05 (I/O e Exceções) A função ler_arquivo() não tem try-except dentro dela, mas a função main() que a chama possui um bloco try-except externo protegendo a chamada. Como a análise é intrafuncional, R05 apontará a chamada interna como desprotegida. Uma função de leitura escrita em uma biblioteca proprietária com nome incomum (fora de IO_CALL_NAMES) não será reconhecida como operação de I/O.
R06 (Validação de Entrada) Uma função chamada check_status() que verifica apenas se a tela está aberta será contada como sinal estrutural de validação pelo nome. Uma validação matemática feita puramente com operações matriciais do NumPy sem usar if/raise, assert ou funções validate_* não será captada pela heurística.
R08 (Treino vs. Inferência) Uma classe PyTorch nn.Module que define o método forward() no mesmo arquivo em que há uma função auxiliar de treinamento acionará alerta de coexistência no mesmo módulo, mesmo que em produção apenas o método de inferência seja invocado. Rotinas de treinamento escritas manualmente em C++/CUDA ou com nomes customizados fora dos indicadores padrão podem não ser detectadas.

Técnico: Rede neural transformadora treinada em grandes volumes textuais.
Simples: Inteligência artificial generativa capaz de redigir e resumir textos.
No TraceAST: Opcional (--with-llm), usado apenas para traduzir achados em texto simples.

14. Prompt

Técnico: Entrada textual estruturada fornecida para condicionar a geração de um LLM.
Simples: As ordens e dados enviados para a IA.
No TraceAST: Definido em system_instruction dentro de llm_agent.py.

15. Token

Técnico: Unidade mínima de subpalavra processada por um modelo de linguagem.
Simples: Pedaço de palavra usado para medir o tamanho do texto lido/gerado pela IA.
No TraceAST: Contabilizado em total_tokens no manifesto.

16. Context Window (Janela de Contexto)

Técnico: Capacidade máxima de tokens que um LLM processa em uma única requisição.
Simples: O tamanho máximo do texto que a IA consegue ler de uma vez.
No TraceAST: Economizada graças ao envio apenas de resumos estruturados.

17. Temperature (Temperatura)

Técnico: Hiperparâmetro que escala os logits antes da amostragem softmax no LLM.
Simples: Controle de criatividade da IA (0.1 = muito focado e previsível).
No TraceAST: Padrão 0.1 configurado em TRACEAST_LLM_TEMPERATURE.

18. API (Application Programming Interface)

Técnico: Interface padronizada de comunicação entre sistemas de software.
Simples: Canal que permite ao Python conversar com um serviço externo.
No TraceAST: Usada apenas quando o usuário ativa a comunicação opcional com a Groq.

19. JSON (JavaScript Object Notation)

Técnico: Formato leve de intercâmbio de dados estruturados em pares chave-valor.
Simples: Arquivo de texto organizado para computadores lerem facilmente.
No TraceAST: Formato de findings.json e dos manifestos.

20. Schema (Esquema)

Técnico: Especificação formal da estrutura, tipos e restrições de um conjunto de dados.
Simples: O "molde obrigatório" que define quais campos um arquivo JSON deve ter.
No TraceAST: Implementado com Pydantic V2 em traceast/models.py.

21. Finding (Achado)

Técnico: Registro consolidado da avaliação de uma regra sobre o repositório.
Simples: O resultado final de cada uma das 8 verificações (TA-001 a TA-008).
No TraceAST: Representado pela classe Finding.

22. Evidence (Evidência)

Técnico: Elemento estrutural observável vinculado a um arquivo e intervalo de linhas.
Simples: A prova concreta (qual arquivo e qual linha) encontrada no código.
No TraceAST: Representada pela classe EvidenceItem.

23. Rule (Regra)

Técnico: Critério determinístico versionado que mapeia evidências a um estado de triagem.
Simples: Cada um dos 8 itens do checklist técnico (R01 a R08).
No TraceAST: Definida em traceast/rule_catalog.py.

24. Precision (Precisão)

Técnico: Razão $TP / (TP + FP)$.
Simples: De tudo que a ferramenta apontou, quantos por cento estavam corretos.
No TraceAST: Calculada em _compute_prf1() no módulo evaluation.py.

25. Recall / Sensitivity (Sensibilidade)

Técnico: Razão $TP / (TP + FN)$.
Simples: De tudo que os especialistas encontraram, quantos por cento a ferramenta detectou.
No TraceAST: Calculada em recall_sensitivity em evaluation.py.

26. F1-score

Técnico: Média harmônica entre Precision e Recall.
Simples: Nota única que resume o equilíbrio entre precisão e sensibilidade.
No TraceAST: Calculada por regra e agregada (micro e macro) em evaluation.py.

27. True Positive (TP)

Técnico: Instância positiva real corretamente classificada como positiva.
Simples: Indicador que existe no código e foi acertadamente apontado pela ferramenta.
No TraceAST: Contabilizado por classify_pair_outcome().

28. False Positive (FP)

Técnico: Instância negativa real incorretamente classificada como positiva.
Simples: Alarme falso apontado pela ferramenta.
No TraceAST: Contabilizado quando a ferramenta aponta presença onde o especialista julgou ausente/inaplicável.

29. False Negative (FN)

Técnico: Instância positiva real incorretamente classificada como negativa.
Simples: Lacuna ou indicador real que a ferramenta deixou escapar.
No TraceAST: Quando o especialista aponta observed/partial e a ferramenta retorna not_observed.

30. Cohen's Kappa ($\kappa$)

Técnico: Estatística de concordância inter-observadores corrigida pelo acaso.
Simples: Mede o quanto dois especialistas humanos concordam além da sorte.
No TraceAST: Calculado pela função compute_cohens_kappa().

31. Bootstrap (Cluster Bootstrap)

Técnico: Método de inferência estatística por reamostragem com reposição de unidades agrupadas.
Simples: Simular centenas de novos estudos sorteando repositórios para medir a margem de incerteza.
No TraceAST: Sorteia repository_id com reposição em score_tool_against_consensus().

32. Confidence Interval (Intervalo de Confiança)

Técnico: Intervalo estimado que cobre o parâmetro populacional com frequência nominal (95%).
Simples: Faixa (mínimo e máximo) que mostra a incerteza estatística da métrica calculada.
No TraceAST: Reportado em confidence_intervals_95.

33. IEC 62304

Técnico: Norma internacional Medical device software — Software life cycle processes.
Simples: O padrão mundial de engenharia para desenvolvimento e manutenção de software médico.
No TraceAST: Referência central de ciclo de vida para as regras R01–R08.

34. SaMD (Software as a Medical Device)

Técnico: Software destinado a um ou mais propósitos médicos sem fazer parte de um hardware médico físico.
Simples: Programa de computador (como uma IA de apoio diagnóstico) que atua como dispositivo médico.
No TraceAST: Público-alvo do sistema de pré-auditoria.

35. ANVISA e RDC 657/2022

Técnico: Agência Nacional de Vigilância Sanitária e resolução que dispõe sobre a regularização de SaMD no Brasil.
Simples: O órgão regulador brasileiro e a regra oficial para registrar softwares médicos no país.
No TraceAST: O PDF oficial da RDC 657/2022 está indexado em legal_documents/RDC_657_2022.pdf.

36. SOUP (Software of Unknown Provenance)

Técnico: Item de software já desenvolvido e geralmente disponível que não foi desenvolvido sob o processo IEC 62304.
Simples: Bibliotecas prontas de terceiros (como PyTorch, NumPy, Pandas) instaladas no projeto.
No TraceAST: Inspecionado pela regra R02.

37. CI/CD (Integração Contínua)

Técnico: Prática de engenharia que automatiza a construção e execução de testes a cada alteração no repositório.
Simples: Robô no GitHub/GitLab que roda os testes automaticamente toda vez que alguém salva código novo.
No TraceAST: Inspecionado pela regra R04.

38. Fixture

Técnico: Estado ou artefato fixo preparado como base reproduzível para execução de testes.
Simples: Repositório de mentira criado com exemplos controlados para testar a ferramenta.
No TraceAST: Localizadas em tests/fixtures/.

39. Pytest

Técnico: Framework de testes automatizados para Python.
Simples: Ferramenta que executa os 15 testes de qualidade do projeto e mostra se passaram.
No TraceAST: Executado via python -m pytest -v.

40. Hash SHA-256 e Commit SHA

Técnico: SHA-256 é uma função criptográfica de resumo de 256 bits; Commit SHA é o identificador da versão no Git.
Simples: A "impressão digital única" de um arquivo ou da versão do projeto; se mudar uma única vírgula no arquivo, o código muda completamente.
No TraceAST: Calculado por compute_sha256() e get_git_commit_sha().

Como Reproduzir uma Execução Cientificamente

Em ciência da computação aplicada à saúde, reprodutibilidade significa que um pesquisador independente, em outro laboratório ou universidade, consegue executar o mesmo protocolo sobre os mesmos dados e obter exatamente os mesmos resultados. Para garantir isso, o arquivo run_manifest.json e o repository_inventory.json registram 12 elementos de auditoria:

Elemento Registrado Campo no Manifesto / Inventário Por que é Indispensável para a Reprodutibilidade Científica
1. Commit SHA do Repositório Analisado commit_sha Prova qual versão exata do código médico foi inspecionada (ex.: 8fa5e256a105...).
2. Hashes SHA-256 dos Arquivos Analisados parsed_files[*].sha256 Mesmo que o repositório não use Git, o SHA-256 de cada arquivo .py prova que nenhuma linha foi alterada.
3. Versão do TraceAST-62304 tool_version Identifica a versão exata da ferramenta (1.0.0).
4. Hash SHA-256 do Catálogo de Regras rule_catalog_sha256 Prova que os textos, critérios e queries das regras R01–R08 (35cab4357bb9...) não foram modificados entre os testes.
5. Hashes SHA-256 da Documentação Regulatória regulatory_documents_sha256 Registra a assinatura digital de cada um dos 26 documentos normativos (ex.: ANVISA_RDC_657_2022: b10b4ab1482b...).
6. Versão do Python e Dependências Fixadas python_version + requirements.txt Documenta o interpretador exato (3.13.14) e as bibliotecas com versão travada (==).
7. Configurações do RAG e Modelo de Embeddings configuration.embedding_model + retrieval_backend Registra qual modelo e qual backend (TF-IDF determinístico ou híbrido denso) calcularam os scores.
8. Auditoria de LLM e Parâmetros llm_usage_audit Comprova se houve uso de API externa (external_api_used: false no modo determinístico) ou registra modelo, temperatura e tokens.
9. Data, Hora UTC e Durações execution_timestamp + durations_seconds Registra o instante exato (ISO 8601 UTC) e o desempenho computacional de cada fase.

19.2 Como Comparar Cientificamente Duas Execuções

Para verificar se duas execuções (run_A e run_B) produziram resultados técnicos idênticos:

  1. Verifique em run_manifest.json se commit_sha, rule_catalog_sha256 e regulatory_documents_sha256 são idênticos.
  2. Compare a lista findings de run_A/findings.json e run_B/findings.json: como o motor é determinístico, todos os campos status, evidence e regulatory_references serão 100% iguais!
