Section 1

Presentation of TraceAST-62304

1.1 What Is TraceAST-62304?

TraceAST-62304 is a computational tool for evidence-traceable pre-audit screening designed for Python source-code repositories that develop Software as a Medical Device (SaMD).

Rather than relying on a generative AI model's intuition to "guess" whether a medical software repository is compliant, TraceAST-62304 inspects the physical and syntactic structure of the repository using Python's native Abstract Syntax Tree (AST), evaluates 8 versioned deterministic rules (R01 through R08), retrieves pertinent excerpts from official regulatory documents (such as ANVISA RDC 657/2022 and verifiable IEC 62304 lifecycle mappings), and generates a structured dossier in JSON and Markdown pointing to the exact file, symbol, and line numbers where each piece of evidence was found.

30-Second Plain-Language Explanation

"Imagine a company developing medical software. Before submitting the project to a formal quality or regulatory evaluation, the team runs TraceAST-62304. The system inspects the repository structure, identifies technical evidence, checks for potential lifecycle gaps, and organizes findings that require human review."

1.2 What Problem Does It Solve and Why Was It Developed?

Medical AI researchers, digital health startups, and academic hospital teams frequently build clinical software in Python (using PyTorch, pydicom, scikit-learn, etc.) while postponing software lifecycle engineering controls required by IEC 62304 and ANVISA RDC 657/2022 until the very end of product development. When they finally prepare for a regulatory audit, they often discover missing dependency pinning (SOUP control), unverified I/O exception paths, missing automated test evidence, or tightly coupled training and inference scripts.

Conversely, pasting raw source code into commercial Large Language Models (LLMs) creates three severe risks: (1) regulatory hallucinations (invented clauses or fabricated line numbers), (2) lack of reproducibility (different answers on every run), and (3) intellectual property exposure. TraceAST-62304 was engineered to solve this exact gap: 100% deterministic, local-first structural extraction paired with verifiable regulatory retrieval.

1.3 Who Can Use It and How Does It Help Medical Software Teams?

  • Software & ML Engineers: Run local pre-audit checks (`python -m traceast scan`) to locate unprotected I/O calls, unpinned dependencies, or training/inference coupling with exact file and line coordinates.
  • Quality Assurance (QA) & Regulatory Affairs Specialists: Receive a structured `report.md` and `findings.json` mapping code-level observations to IEC 62304 sections and ANVISA RDC 657/2022 articles.
  • Scientific Researchers & Auditors: Use the reproducibility manifests (`run_manifest.json`, `retrieval_trace.json`) and statistical evaluation engine (traceast/evaluation.py) to benchmark screening performance against human expert consensus.

1.4 Why It Is a Pre-Audit Screening Tool — Not an Automated Regulatory Auditor

7 Mandatory Regulatory Guardrails
  1. Never replaces human auditors or regulatory affairs professionals.
  2. Never declares a product certified or in regulatory compliance.
  3. Never automatically determines regulatory risk class (RDC 657/2022 Classes I–IV) or software safety class (IEC 62304 Classes A, B, or C).
  4. Never interprets the absence of code evidence (not_observed) as proof of non-compliance (since QMS documents often live outside the code repository).
  5. Never generates regulatory requirements without a verifiable reference.
  6. Never invents clauses, documents, features, or evidence.
  7. Never makes claims about clinical performance, clinical safety, or diagnostic efficacy from static code analysis.

Section 6

How Static Analysis & the AST Visitor Work

6.1 What Is an Abstract Syntax Tree (AST)?

An Abstract Syntax Tree (AST) is the hierarchical tree representation that Python's compiler builds when reading source code via ast.parse(source_text). Instead of searching text with fragile regular expressions—which easily confuse a real function call like torch.load("model.pt") with a comment or docstring mentioning "torch.load"—the AST distinguishes true executable syntactic nodes (ast.Call, ast.Try, ast.FunctionDef, ast.AsyncFunctionDef) from strings and comments.

Concrete Example: Why Docstrings Never Trigger False Positives in TraceAST-62304

In tests/fixtures/repo_false_positive_traps/scheduler.py, a docstring contains the text "Does NOT call torch.load('weights.pt') or open('patient.dcm')". Because _RecursiveASTVisitor in traceast/ast_analyzer.py only records I/O and model operations when visiting an actual ast.Call node (and ignores docstring ast.Constant nodes), io_operations and model_artifacts remain 0, preventing false positives (verified by test_08).

6.2 How _RecursiveASTVisitor Tracks Scope, Nested Functions, and Try-Except Blocks

Implemented in traceast/ast_analyzer.py (lines 99–361), _RecursiveASTVisitor subclasses ast.NodeVisitor and maintains two internal stacks while walking every node:

  • self._scope_stack: List[Tuple[str, str]] — Tracks the current chain of enclosing classes and functions (e.g., [("class", "ChestDiagnosticModel"), ("async_method", "async_predict_study")]), enabling accurate qualified symbol names such as validate_dicom_input._nested_range_validator and ChestDiagnosticModel.async_predict_study.
  • self._try_stack: List[Dict[str, Any]] — Tracks active ast.Try blocks. Whenever a candidate I/O call is visited inside visit_Call, the visitor checks any(t["is_non_empty_and_non_pass"] for t in self._try_stack) to set inside_non_empty_try.

Section 8

How Regulatory RAG & Hybrid Retrieval Work

Implemented in traceast/rag_engine.py, RegulatoryRAGEngine indexes the local normative corpus inside legal_documents/:

  • Corpus Size Verified in Production (retrieval_trace.json): 26 indexed documents (1 official PDF of ANVISA RDC 657/2022 + 25 OpenRegulatory IEC 62304 / AI-ML Markdown templates) segmented into 257 traceable chunks.
  • Explicit FDA Exclusion in V1.0: Any file inside legal_documents/FDA/ is skipped via if "FDA" in md_path.parts: continue, enforcing the v1.0 regulatory scope decision.
  • Per-Rule Bilingual Retrieval (top_k=3): Rather than issuing a single generic search for the whole repository, the engine executes a specific bilingual query (rag_query_pt + rag_query_en) for each applicable rule (R01–R08), scoring every chunk via a deterministic combination of Okapi BM25 lexical relevance (55%) + character 3–4-gram TF-IDF cosine similarity (45%) + normative scope bonus (+0.18).
Section 9

How the Optional LLM Module Works & Its Safety Guardrails

Implemented in traceast/llm_agent.py, the LLM module is disabled by default (TRACEAST_ENABLE_LLM=false) and only runs when --with-llm is explicitly passed. It enforces four strict engineering guardrails:

  1. Payload Sanitization (build_sanitized_llm_payload): Never sends raw Python code or docstrings. When allow_code_excerpts=False (default), internal file paths and symbols are masked as file_1.py and symbol_1.
  2. Restrictive System Prompt (SYSTEM_PROMPT): Prohibits regulatory certification claims, invented clauses, or status overrides.
  3. Pydantic Output Validation (LLMExplanation): Parses JSON responses into accessible_explanation, suggested_documents_to_review, and preliminary_corrective_actions.
  4. Immutability of Deterministic Status: Uses finding.model_copy(update={"llm_explanation": explanation_obj}) so finding.status, finding.evidence, and finding.regulatory_references can never be modified by the LLM.

Understanding the Structured JSON Output (findings.json)

Every execution generates findings.json, validated by FindingsReport in traceast/models.py. Each finding contains: finding_id (TA-001..TA-008), rule_id (R01..R08), status, status_label_pt, review_priority, confidence, description, justification, evidence (with exact file, symbol, line_start, line_end), regulatory_references (with chunk_id, document_hash, and similarity_score), limitations, recommended_action, and human_review_required: true.

Section 12

System & Scientific Metrics — Complete 7-Part Didactic Guide

Every metric implemented in traceast/ast_analyzer.py, traceast/rag_engine.py, and traceast/evaluation.py is explained below using the mandatory 7-part pedagogical structure: (1) What it measures, (2) Why it matters, (3) How it is computed in code, (4) Mathematical formula, (5) Step-by-step numerical example, (6) How to interpret the result, and (7) Methodological limitations.

12.1 Precision, Recall (Sensitivity), F1-Score, and Confusion Matrix (TP, FP, TN, FN)

  • 1. What they measure: How accurately TraceAST-62304's deterministic findings agree with the human specialist consensus reference standard (VALIDATION_PROTOCOL.md | PT-BR).
  • 2. Why they matter: In pre-audit screening, Recall measures whether real technical gaps are caught before a formal audit, while Precision measures whether developer review time is protected against false alarms.
  • 3. How they are computed in code: Implemented in classify_pair_outcome() and score_tool_against_consensus() in traceast/evaluation.py. Crucially, when human consensus marks a rule as not_applicable or unable_to_assess, a tool output of not_observed or not_applicable is scored as a True Negative (TN) and never penalized as a False Negative (FN).
  • 4. Mathematical Formulas:
    $$\text{Precision} = \frac{TP}{TP + FP}, \qquad \text{Recall} = \frac{TP}{TP + FN}, \qquad \text{F1-Score} = 2 \cdot \frac{\text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}}$$
  • 5. Step-by-Step Numerical Example (Mandatory Didactic Scenario): Suppose human specialists inspect a set of repositories and identify 10 real technical indicators/gaps ($TP + FN = 10$). TraceAST-62304 flags 8 indicators ($TP + FP = 8$), of which 6 are confirmed as true positives ($TP = 6$):
    • True Positives ($TP$) = 6 (correctly flagged indicators).
    • False Positives ($FP$) = $8 - 6 =$ 2 (flagged by the tool, but not confirmed by specialists).
    • False Negatives ($FN$) = $10 - 6 =$ 4 (real indicators missed by the tool).
    • $\text{Precision} = \frac{6}{6 + 2} = \frac{6}{8} = 0.75 = \mathbf{75.0\%}$.
    • $\text{Recall} = \frac{6}{6 + 4} = \frac{6}{10} = 0.60 = \mathbf{60.0\%}$.
    • $\text{F1-Score} = 2 \cdot \frac{0.75 \times 0.60}{0.75 + 0.60} = \frac{0.90}{1.35} \approx 0.6667 = \mathbf{66.67\%}$.
  • 6. How to interpret: Values closer to $1.0$ ($100\%$) indicate stronger alignment with human specialists.
  • 7. Limitations: Depends on the quality and independence of the human reference standard.

12.2 Inter-Rater Agreement — Cohen's Kappa ($\kappa$)

  • 1. What it measures: Agreement between Independent Reviewer 1 and Independent Reviewer 2 beyond chance before adjudication.
  • 2. Why it matters: Validates that the human reference standard itself is reliable and reproducible.
  • 3. How it is computed in code: compute_cohens_kappa(labels_a, labels_b) in traceast/evaluation.py.
  • 4. Mathematical Formula: $\kappa = \frac{P_o - P_e}{1 - P_e}$, where $P_o$ is observed agreement and $P_e$ is chance agreement.
  • 5. Numerical Example: If two reviewers evaluate 20 items, agree on 17 ($P_o = 17/20 = 0.85$), and expected chance agreement from marginal totals is $P_e = 0.50$, then $\kappa = \frac{0.85 - 0.50}{1 - 0.50} = \frac{0.35}{0.50} = \mathbf{0.70}$ (substantial agreement).
  • 6. Interpretation: $\kappa > 0.60$ indicates substantial agreement; $\kappa > 0.80$ indicates near-perfect agreement.
  • 7. Limitations: Sensitive to highly skewed class distributions.

12.3 95% Confidence Intervals via Cluster Bootstrap by Repository

  • 1. What it measures: Statistical uncertainty bounds (2.5th and 97.5th percentiles) around Precision, Recall, and F1.
  • 2. Why it matters: Because all 8 rules (`R01`–`R08`) evaluated on the same repository share the same codebase and author team, they are correlated within that repository. Resampling whole repositories (`repository_id`) with replacement ($B=1000$, `seed=42`) in cluster_bootstrap_ci() (traceast/evaluation.py) prevents artificially narrow confidence intervals.

12.4 Regulatory Retrieval Recall@3 (hit_rate_recall_at_k and mean_fractional_recall_at_k)

  • 1. What it measures: Whether the top $k=3$ chunks retrieved by RegulatoryRAGEngine for each rule (`R01`–`R08`) contain the expected normative reference documents.
  • 2. Formula & Real Result: $\text{Hit Rate Recall@3} = \frac{1}{|Q|}\sum_{q=1}^{|Q|} \mathbb{I}(\text{hit in top 3})$. In evaluation_artifacts/rag_recall_at_3_evaluation.json, TraceAST-62304 achieves Hit Rate Recall@3 = 1.0 (8/8 queries) and Mean Fractional Recall@3 = 0.9375 (93.75%).

12.5 Planned / Theoretical Metrics Not Implemented in V1.0

Transparency Note on Unimplemented Theoretical Metrics

In accordance with the repository's strict truthfulness policy, the following metrics from earlier conceptual drafts are not implemented in the v1.0 codebase: (1) character-reduction percentage of raw AST skeletons, (2) multi-run Jaccard stability index (not needed because the v1.0 pipeline is 100% deterministic), (3) per-file latency median/standard deviation (v1.0 records per-stage durations in stage_durations_seconds), and (4) estimated_cost_usd (v1.0 records exact token counts prompt_tokens, completion_tokens, and total_tokens).

Non-parametric resampling method that resamples entire repositories with replacement to compute valid 95% confidence intervals.
